# Stage 5 — Agent Orchestrator

Оркестратор — системный слой, не девятый сотрудник. Утверждённая графика, восемь IDs/ролей, профили, Skills и индивидуальные сессии сохранены. Новых прав агентам нет: Stage 5 координирует **read-only анализ**, а не изменение файлов проекта. Stage 6 не реализован.

## Использование

1. `npm run build`, затем `npm run bridge`. В строке запуска: `Stage 5 orchestrator`. Открыть `http://127.0.0.1:8787/`.
2. Под офисом раскрыть **Team workflow · оркестратор**. В Mock выбрать сценарий и начать задачу; кнопка **Следующий mock-шаг** подтверждает следующий детерминированный результат. Это не запуск Codex.
3. Для настоящего выполнения переключить офис в Codex, подключить сотрудников и начать командную задачу. Подключение не запускает модель. Только явный старт workflow разрешает планирование и зависимые запуски.
4. В графе раскрыть задачу: исполнитель, Skills, зависимости/блокировки, статус, execution ID, ошибки, checkpoint, переданный контекст и результат. Пауза/продолжение/отмена управляют всем workflow. При recoverable ошибке сначала явный Retry, затем Resume.
5. После перезапуска workflow восстанавливается **на паузе**, без автоматического запуска. Подключить сотрудников, проверить checkpoints, нажать **Продолжить workflow**. Законченные задачи повторно не запускаются.

Старый демонстрационный workflow и индивидуальные задания остаются доступны, но не запускайте их одновременно с командной задачей в Mock. Занятый или приостановленный сотрудник не получает новую задачу. Историю не сбрасывать, пока есть незавершённый workflow. В реальном режиме мост блокирует индивидуальный новый Start, пока workflow открыт; существующие controls доступны для безопасной остановки и диагностики.

## Слои

`WorkflowPanel → WorkflowClient → Orchestrator → ExecutionPort`

- `src/orchestration/model.ts`: контракты, проверка плана/DAG, роли/Skills, выбор свободного сотрудника, ограниченный контекст, сбор результата, проверка сохранённых данных.
- `Orchestrator.ts`: сериализованный планировщик, lifecycle, события, admission, intentions-before-side-effects, пауза/отмена/повтор/восстановление. Независим от React, HTTP и протокола Codex.
- `server/orchestration.mjs`: RealExecutionPort → прежний TeamRuntime → CheckpointPilot → AppServerRpc. Отдельное atomic-хранилище `.ai-office/workflows.json` под прежним единственным bridge writer lock.
- `MockExecutionPort.ts`: тот же контракт и тот же Orchestrator, прежний MockCodexAdapter / TaskSystem и checkpoints Stage 4B; localStorage workflow отдельно от старого recovery key. Mock-сценарии не используются как реальные планы.
- Новый HTTP-контракт только `/api/workflows/snapshot` и `/api/workflows/action`, с прежними Host/Origin/nonce-проверками. Вход ≤8 KB; конечный allowlist команд; нет shell/RPC/grant или пользовательского выбора файлов.

Реальные `thread/start`, `turn/start`, `thread/resume`, `turn/interrupt`, профили, явные Skill inputs и политика read-only остаются прежними. Новые поля в API Codex не придуманы. Проверенная версия CLI: 0.144.5. Источник: [официальная документация App Server](https://learn.chatgpt.com/docs/app-server); локальная схема установленной версии имеет приоритет над новыми возможностями документации.

## План и модель

Workflow: ID, project ID, source, root task, priority, status, subtasks, planned flag, error, created/started/completed timestamps, workflow checkpoint.

Subtask: ID/title/description/type, assigned employee, required Skills, permissions, dependencies, priority, lifecycle, bounded input context, result, classified error, execution ID, attempts, employee checkpoint ID, timestamps.

Lifecycle: `pending → ready → launching → running → completed`; также `paused`, `failed`, `cancelled`. `launching` записывается **до** обращения к runtime. ID исполнения содержит workflow/task/attempt; повторный вызов с тем же ID отклоняется runtime. Новый root request с прежним ID идемпотентен только при совпадении текста. Один открытый workflow на проект, максимум 30 записей истории, до 16 рабочих subtasks плюс один планировщик. Новые задачи может создать только один проверенный ответ планировщика; рабочие ответы не могут создавать или делегировать задачи.

Lead получает реальную root task и каталог разрешённых типов. Возвращает JSON-граф. Проверяются точные поля, уникальные IDs, существование зависимостей, отсутствие циклов, read-only permissions, известные типы и принадлежность требуемых Skills соответствующей роли. После этого задачи получают существующий employee ID из каталога capabilities. В графе нет постоянно зашитой цепочки сотрудников; независимые ветви и количество задач определяются конкретным ответом Lead. Фиксирован только каталог компетенций восьми неизменных ролей.

Scheduler дополнительно проверяет подключение, реальные обнаруженные Skills, отсутствие ошибки recovery и состояние idle/completed. Paused/error/занятый сотрудник не считается доступным; задача ждёт. Неродственную работу свободному сотруднику не передают. Переназначение другой роли автоматически не выполняется: без подходящего равноценного сотрудника безопасное продолжение — остановка и решение Director.

## Результаты и события

Результат содержит summary, filesChanged, decisions, warnings, unresolved. Read-only задача не может достоверно изменить файлы, поэтому filesChanged всегда пуст; ответ с заявленными изменениями отклоняется. Работник получает запрос структурированного JSON. Неструктурированный ответ сохраняется с явным unresolved-предупреждением, а не с вымышленными решениями. Ответы — заявления модели, не свидетельство выполненных внешних проверок.

Dependent получает только root task и **прямые** upstream результаты с ID источника. Summary/списки ограничены по общему бюджету; короткие списки решений и предупреждений сохраняются целиком, усечённые строки имеют отметку `[…]`. Полная версия доступна в результате исходной задачи. История разговоров, credentials, arbitrary file paths и приватное recovery-хранилище не передаются. Свежие хешированные снимки разрешённых исходников и свои проверенные Skills загружаются прежним bridge. Недоверенные результаты не расширяют разрешения. Известные формы секретов редактируются; root request с такими данными отклоняется. Это защита известных шаблонов, не гарантия распознавания любого возможного секрета: не вводить credentials в задачи.

События workflow_created, plan_generated, task_assigned, dependency_satisfied, task_started/completed/paused/resumed/failed, approval_requested/rejected, task_retry_requested, workflow_pause_requested/paused/resumed/cancelled/completed сохраняются и попадают в прежний Team Activity. Оркестратор не генерирует проценты по времени; UI показывает состояние графа и реальные runtime-состояния.

## Ошибки, права и остановка

- Completion требует терминального подтверждения Codex и непустого результата; ответ с невалидным планом — permanent failure.
- Pause сохраняет существующий Stage 4B checkpoint; пока остановка не подтверждена, слот занят. Зависимые задачи не стартуют. При проблеме workflow консервативно приостанавливается целиком, сохраняя завершённые результаты.
- Usage limit определяется прежним проверенным CodexErrorInfo, не текстом или таймаутом. Disconnect сохраняет checkpoint; не объявляется успехом.
- Recoverable error требует явного Retry; максимум три попытки суммарно. Автоматического повтора нет. Если runtime сохранил paused execution, Retry ведёт к продолжению этого же checkpoint, а не новому запуску.
- Approval request блокирует задачу и workflow. Оркестратор не отвечает на запрос без решения Director. Прежняя read-only политика позволяет **отклонить дополнительные права** и продолжить исходную задачу. Кнопки выдачи shell/write/network прав нет. Если без расширения прав задача невозможна, её нужно отменить; это не повод обходить ограничение.
- Cancel останавливает реальные активные turn, ждёт подтверждения и закрывает owned checkpoints как не возобновляемые. Результаты законченных задач сохраняются. Неизвестную живую операцию нельзя незаметно считать отменённой.
- При отказе workflow-хранилища новые запуски блокируются, исходный файл не удаляется. Уже запущенный сотрудник сохраняет Stage 4B recovery отдельно; его можно остановить прежними индивидуальными controls. Нужен ремонт хранилища, затем перезапуск.
- Если после сбоя execution отсутствует или уже заменён индивидуальной работой, система не создаёт дубликат. Необходима проверка Director. При подтверждённом сохранённом завершении можно использовать последнюю сохранённую заметку; если полный результат утрачен в окне между терминальным событием и сохранением workflow, автоматическое продолжение блокируется.

## Конкурентность и границы

Максимум два активных запуска **вместе с индивидуальными заданиями**; `AI_OFFICE_MAX_ACTIVE=1` включает последовательный режим. Дополнительно прежний TeamRuntime атомарно резервирует слот перед async-запуском. Модельные работники не получают multi_agent или автоматическое делегирование. Граф выполняется единственным серверным scheduler под bridge lock; разные browser tabs не создают дополнительные реальные запуски.

Mock предназначен для одной открытой управляющей вкладки. В нём manual advance обеспечивает предсказуемые сценарии, ошибки/approval явно симулируются. При настоящем Codex нет mock-ответов или подмены сбоя симуляцией. Никаких файлов проекта агентам изменять не разрешено. Сохраняются ранее документированные ограничения доверия к локальному пользователю и окружению процесса; Stage 5 не является полной изоляцией от вредоносной программы того же Windows-пользователя.

`tests/orchestrator-server.test.mjs`: RealExecutionPort через прежний RPC-контракт с транспортным дублёром, owned execution IDs/Skills, реальные механизмы Stage 4B pause/resume, HTTP-boundaries и atomic file storage. Это автоматизированная проверка контракта, не утверждение о запуске живой модели. Прежние team/checkpoint тесты продолжают проверять всех восьмерых индивидуально.
