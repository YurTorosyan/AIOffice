# AI Office P0 сохранность и эффекты

**Статус: план для согласования, реализация не начата. Версия 0.1. Дата: 19 ноября 2026 года.**

Основание — [единый контракт версии 0.1](STABILIZATION_CONTRACT_DRAFT.md), утверждённый Director вместе с D1–D8. Здесь определены точные файлы, изменения, порядок и условия приёмки первого пакета. Список файлов — граница будущей реализации, а не перечень уже внесённых изменений.

## 1. Результат P0

После реализации P0 ответ модели, действие с файлами и состояние workflow должны переживать предусмотренные сбои без потери подтверждённых данных и повторения побочного эффекта. Ошибка ответа не должна делать хранилище невалидным. Неизвестный исход должен иметь штатный путь сверки, а не требовать ручной правки JSON.

P0 не перестраивает планировщик, комплектование контекста, модельные бюджеты и правила качества. Они остаются для P1/P2. Полное переоформление панели и система метрик остаются для P3. В P0 нужны только элементы UI, без которых восстановление приходится делать вручную.

| В P0 | За пределами P0 |
|---|---|
| Полный безопасный архив ответов на границе runtime | Новая классификация задач и выбор моделей |
| Транзакционное принятие ответа и checkpoint | Новый планировщик больших проектов |
| Журнал согласованных эффектов и их сверка | Увеличение лимитов файлов, patch или prompt |
| Точные подтверждения и защита от повторов | Изменение реализации ARMGARAGE |
| Восстановление после restart, частичного эффекта и случайной отмены | Запуск реальных контрольных задач Codex |
| Минимальное объяснение причины и безопасное действие восстановления | Новые полномочия, shell, зависимости, Git или публикация |

## 3. Технические решения в границах контракта

### 3.1 Разные факты и один подтверждённый переход

Вводятся внутренние записи о сохранности и эффектах без массового переименования существующих статусов. Завершение turn, сохранение ответа, принятие ответа и применение diff имеют отдельные подтверждения. Старые поля сохраняются через совместимое представление.

Для перехода workflow: создать временное новое состояние → проверить целиком → сохранить с ожидаемой версией предыдущего снимка → опубликовать его в памяти/UI. Ошибка записи не должна оставлять новое неподтверждённое состояние в роли последнего сохранённого. Разрешается отдельно показать наблюдённый ответ с признаком «ещё не зафиксирован».

Между отдельными JSON-файлами не обещается общая файловая транзакция. Связность восстанавливается по журналу операции, ссылкам на архивы, версиям снимков и квитанциям. До сверки новые эффекты запрещены.

### 3.2 Архив на границе получения ответа

Полный безопасный ответ фиксируется при получении соответствующего терминального сообщения, до UI-preview, кратких заметок и валидации бизнес-содержания. Sink привязан к execution ID и сохраняется до подтверждённой записи; он не должен зависеть от временной mutable-настройки выбранного сотрудника.

Дескриптор архива содержит владельца проекта/workspace/задачи/сотрудника, execution/thread/turn IDs, hash, размер, версию и состояние содержимого: `complete`, `redacted`, `truncated` либо `unavailable`. Эти названия — внутренние поля AI Office, не API Codex. Неполный/редактированный ответ нельзя выдать за дословный полный оригинал. При превышении существующего предела или секретных данных выполняется безопасный отказ с явной причиной; предел не повышается молча.

Восстановление читает проверенный архив по server-owned ID. Наличие непустой 5 000-символьной заметки не доказывает полноту ответа. Заметки остаются кратким контекстом. Исторический ответ без полного артефакта получает явный статус недостаточности, а не выдуманный результат.

### 3.3 Устойчивая операция и точное разрешение

Сервер создаёт operation ID один раз для конкретного намерения и версии предложения. Он связывается с project/workflow/task, action, исходными хешами, fingerprint полного payload, policy version и историей подтверждений. Transport request ID служит защитой от дублей запроса, но не заменяет operation ID. Два одинаковых HTTP-запроса не создают две операции.

Порядок: проверить весь набор ресурсов → зафиксировать намерение → зафиксировать точное решение/связь grants с операцией → выполнить ограниченный эффект → сохранить наблюдаемый результат/receipt → обновить workflow. Сбой на любой границе даёт проверяемый этап восстановления. Нельзя сначала потратить grants, а затем обнаружить, что журнал операции вообще не создан.

Повтор завершённой операции возвращает её квитанцию. Если текущие файлы уже другой ревизии, квитанция остаётся историческим фактом, а её применимость к текущему состоянию отмечается отдельно; завершённый эффект не становится поводом повторной записи.

### 3.4 Сверка без автоматического применения

План восстановления сначала только читает и классифицирует:

| Наблюдение | Решение |
|---|---|
| Есть валидный receipt завершённой операции | Восстановить метаданные workflow по receipt; эффект не повторять |
| Файл совпадает с согласованным after hash, receipt не успел сохраниться | Зафиксировать наблюдаемый postcondition, отличая его от достоверно записанной ранее квитанции; не записывать файл снова |
| Файл совпадает с before hash | Эта часть ещё может требовать выполнения; включить её в точный отчёт оставшегося действия |
| Файл не совпадает ни с before, ни с after | Конфликт; не перезаписывать и не откатывать |
| Исход команды или остановки контейнера неизвестен | Не запускать команду повторно; проверять только принадлежащую операции среду и сохранённые свидетельства |
| Имеющихся данных недостаточно | Сохранить UNKNOWN/BLOCKED и конкретную причину; не угадывать успех |

Для оставшихся файлов частичного применения предлагается **отдельное явное recovery-подтверждение**, связанное с исходным operation ID и неизменным общим payload. UI показывает только остающийся эффект и уже выполненную часть. Просроченное/consumed разрешение не оживает. Это уточнение реализации D3/D4, предлагаемое к согласованию вместе с P0.

У неизвестного тестового запуска новый запуск возможен только как отдельное явно согласованное действие после подтверждённой остановки старого. Он не превращает неизвестный старый результат в PASS. Квитанции QA сохраняют нынешние статусы; неопределённость эффекта фиксируется отдельно и блокирует ложное успешное evidence.

До создания контейнера сохраняются его запланированное имя и служебные owner/operation labels; фактический container ID добавляется только после подтверждения среды. Если нужен cleanup после аварии, предлагается отдельное подтверждение конкретного служебного действия над проверенным контейнером этой операции. Оно не запускает тест повторно. Одного похожего имени недостаточно для удаления; Docker arguments не принимаются из браузера или ответа модели.

### 3.5 Отмена, версии и границы среды

Восстановление отменённого workflow возвращает на паузу только допустимые оставшиеся этапы. Никогда не запущенные задачи можно подготовить к продолжению. Ранее запущенное исполнение сначала сверяется; закрытое/неопределённое исполнение не превращается автоматически в новую задачу `pending`. Нужен отдельный план, если для продолжения действительно требуется новый turn.

Отмена и её восстановление остаются событиями истории. Применённые файлы и ответы не откатываются, разрешения не восстанавливаются. Если в проекте уже есть другой открытый workflow, восстановление не подменяет его автоматически.

Поддерживаемые старые записи читаются адаптером совместимости. Отсутствующий новый receipt/ref означает «не доказано», а не «выполнено». Неизвестная версия и повреждённые записи не затираются. Сверка или миграция требуют backup и отдельного подтверждённого плана; загрузка не запускает неявную массовую миграцию.

Защита рассчитана на доверенное локальное окружение и контролируемые сбои при доступном носителе. Полная потеря носителя, недоверенный локальный администратор и глобальное exactly-once для внешней системы не объявляются решёнными P0. База данных или новый облачный сервис в пакет не добавляются.

| `src/ui/WorkflowPanel.tsx` | Небольшой блок: сохранено/не сохранено, неизвестный эффект, инспекция и подтверждение server-owned recovery plan, список уже выполненного/остатка | Пользователь восстанавливает fixture без правки JSON; никаких автозапусков и редизайна офиса |

Внутренние HTTP-названия и точные сигнатуры закрепляются при реализации моделей. Они не являются новыми методами Codex. Любая команда восстановления принимает IDs/версию server-owned плана, а не произвольное содержимое файлов от клиента. Metadata-only подтверждение восстановления не применяет файлы; для оставшегося эффекта создаётся отдельный точный запрос.

## 6. Последовательность реализации

| Шаг | Рабочая область | Проверяемый выход перед следующим шагом |
|---|---|---|
| P0.1 | `durability.ts`, `recovery.ts`, общие JSON stores и fixtures | Детерминированные модели, version guards, read-only recovery plan; последний валидный снимок сохраняется при отказе |
| P0.2 | Runtime → result archive → checkpoint → real port | Безопасный полный ответ доступен после restart без повторного turn; неизвестная полнота не маскируется |
| P0.3 | Operation store/reconciler, permissions и TeamActions | Намерение до эффекта; точное согласие; per-file сверка и receipt replay без дублей |
| P0.4 | Orchestrator/project recovery и QA operation identity | Связное восстановление metadata, отмены и неизвестных QA-запусков без новых effects |
| P0.5 | HTTP/client/minimal UI и crash/browser matrix | Штатное восстановление через UI; собраны доказательства и выполнены критерии P0 |

Каждый шаг — отдельный проверяемый diff. Не начинаем следующий на невалидной модели предыдущего. Точные внутренние схемы и таблицы переходов становятся первым результатом P0.1; техническая детализация не может расширять согласованные полномочия или список production-файлов без обновления плана.

## 7. Сценарии и критерии приёмки P0

P0 закрывает прежде всего S02, S07, S09–S10, S13–S26, S33 и S34 в части сохранности, разрешений и эффектов. S01/S08/S11–S12/S28/S35/S36 служат регрессиями на границах P0. Полное покрытие контекста, budgets, качества и наблюдаемости этих сценариев остаётся P1–P3. Завершение P0 не означает прохождение всей матрицы S01–S36.

| Критерий | Обязательное утверждение | Сценарии контракта |
|---|---|---|
| A01 · Ответ не теряется | Полученный безопасный ответ в существующем допустимом размере сохраняется до бизнес-валидации; hash/owner/полнота проверяемы после restart | S09, S13, S22 |
| A02 · Валидация не портит book | Невалидный ответ отклонён, последняя сохранённая структура читается; validation error отличима от IO error | S09–S10, S23 |
| A03 · Согласие точное | Нельзя заменить payload, владельца, workspace, политику, scope или использовать истёкшее/consumed согласие для нового эффекта | S07, S15–S16, S20 |
| A04 · Один эффект | Двойной approve и потерянный HTTP-ответ не увеличивают число файловых записей/команд; используется исходный operation ID | S14, S19, S33 |
| A05 · Частичность восстанавливается | При прерывании после каждого файла выполненная часть не записывается снова; постороннее изменение остаётся нетронутым | S17–S18 |
| A06 · UNKNOWN честный | Неизвестный запуск/эффект не становится успехом, recoverable retry или основанием для нового start без доказательств | S21–S22, S34 |
| A07 · Снимок не затирается | При отказе записи, rename и повреждении данных остаются исходник/backup и объяснимый recovery plan либо безопасный отказ | S23–S24 |
| A08 · Пауза и отмена безопасны | Возвращается только выбранная работа на паузе; completed результаты и файлы не переигрываются, разрешения не оживают | S25–S26 |
| A09 · Изоляция сохранена | Проверки не переходят на хост, профили/команды/image не подменяются; неподтверждённый cleanup остаётся блокером | S20, S34 |
| A10 · Есть штатный путь | Поддерживаемый случай восстановления проходит через отчёт и точное подтверждение в UI без редактирования JSON, switch/archive обходов и нового модельного turn | S14, S17, S21–S26, S36 |
| A11 · Совместимость честная | Старые поддерживаемые records читаются, недостающие доказательства явно помечены; новая схема не делает старое pending-согласие действующим | S15, S24 |
| A12 · Нет регрессии workflow | Mock полный цикл и прежние plan/context/proposal/gate сценарии сохраняют смысл; нет ложного COMPLETED из-за изменения persistence | S01, S08, S11–S12, S28 |

### Обязательные crash windows

| Failpoint | Где прерывается тестовый процесс | Что обязано восстановиться |
|---|---|---|
| F01 | После полного terminal payload, до фиксации workflow | Архив/признак его незафиксированности; тот же execution ID; без повторного turn |
| F02 | Во время temp/flush/rename архива или checkpoint | Последний валидный объект; незавершённый temp не объявлен полным |
| F03 | После intent, до отправки runtime start | Доказанное отсутствие отправки либо UNKNOWN; без слепого start |
| F04 | После отправки start, до получения ack | Сверка исходного исполнения; отсутствие второго turn/start |
| F05 | Между intent, решением grants и первым эффектом | Связанный план восстановления; отсутствие потраченных «в никуда» прав и неподтверждённого эффекта |
| F06 | После каждого replace файла, до его записи в журнал | Определение before/after/conflict; выполненный файл не записывается снова |
| F07 | После последнего файла, до receipt или workflow commit | Возврат наблюдаемого результата/квитанции и metadata-only восстановление |
| F08 | После запуска QA, до результата или до cleanup ack | Идентификация только своего запуска; UNKNOWN/BLOCKED, без повторного теста и host fallback |
| F09 | Во время pause/cancel/restore commit | Согласованное старое или новое состояние; не полувосстановленный граф с ожившими approvals |
| F10 | Эффект выполнен, HTTP-ответ потерян | Повтор запроса получает тот же результат; фактический effect count остаётся 1 |

Fault injection покрывает временную Windows-блокировку и окончательные IO-ошибки отдельно. После crash проверяет другой процесс, а не исходный объект в памяти. Каждое утверждение о записи/команде подтверждается независимым счётчиком тестового executor и хешами, а не только строкой лога.

## 8. Точный план проверки после реализации

Все проверки — будущие, сейчас они не выполняются.

1. **Изолированная копия.** Создать отдельную рабочую копию согласованной ревизии, без `.ai-office`, пользовательских session/credentials, `qst/`, runtime-процессов и данных ARMGARAGE/Coffee House. Все тестовые корни проверяются на принадлежность этой копии. Проектный bridge на порту 8787 не используется.
2. **Модели и stores.** Запустить новые durability/operation/recovery тесты и дополненные тесты соответствующего шага. При провале исправить этот шаг, не повторять несвязанные проверки без основания.
3. **RPC и HTTP fixtures.** Использовать транспортные дублёры с настоящими адаптерами, `port: 0`, отдельные проекты A/B, fake clocks. Проверить ownership, duplicate requests, restart и recovery leases. Никакого `codex login`, model turn или нового thread реального сотрудника.
4. **Crash matrix.** Пройти F01–F10 с явной точкой сбоя. P0-набор должен пройти в двух полных прогонах при слотах 1 и 2. Окна F01–F04, F06–F07 и F10, соответствующие критическим S14, S17, S21–S23, дополнительно проходят по 10 ограниченных повторений с seed 1–10; нечётные seed — со слотом 1, чётные — со слотами 2. Фактическая точка сбоя и seed записываются в Evidence. Это не повторный прогон всего старого набора тестов 10 раз.
5. **QA lifecycle.** В основном наборе использовать контролируемый command adapter. Если требуется подтверждение реального container lifecycle, отдельно запустить минимальный доверенный fixture в уже проверенной среде с собственным operation label; никаких тестов ARMGARAGE, изменения images или удаления чужих контейнеров. При недоступной среде нельзя заявлять реальную проверку cleanup пройденной.
6. **Регрессии и build.** В изолированной копии один раз выполнить весь существующий `npm test` и `npm run build` после финального изменения. Hooks проверки Skills не должны работать с файлами активной копии. Дополнительный полный прогон нужен только при новой причине; существующие тесты не выдают за доказательство crash windows без новых assertions.
7. **Браузер.** `scripts/verify-p0-recovery-browser.mjs`: искусственные состояния, свежий профиль, восемь работников, понятные UNKNOWN/unsaved и допустимые действия. Проверить reload, возврат результата дублированного запроса, preview восстановления и отсутствие авто-approve/auto-start. Не управлять текущей вкладкой пользователя.
8. **Отчёт.** Записать версию, scope, команды, результаты, seeds/failpoints, hashes и известные границы в Evidence-файлы. Проверить diff: только согласованный список, без runtime state, секретов и посторонних файлов.

Реальные контрольные задачи Codex относятся к P4 и не запускаются для приёмки P0. Изолированный контейнерный fixture из пункта 5 — отдельная техническая проверка, а не продолжение живого QA workflow.

## 9. Совместимость и ввод в работу

Работа P0 в отдельной копии не обновляет работающий мост и не мигрирует текущие workflow. Изменения не подхватываются живой Vite-вкладкой пользователя.

После прохождения A01–A12 предлагается отдельный план ввода: остановка только в согласованное окно, backup выбранных stores, сравнение версий, dry-run миграции, проверка связей архивов/операций и запуск на паузе. Открытый ARMGARAGE нельзя незаметно переключить на новую политику или схему. Если перенос активного проекта требует изменения записей, точный diff состояния согласуется отдельно.

Откат не означает удаление новых receipts или отмену применённых файлов. Если старый код не понимает новые записи, повторный запуск старого writer запрещён до согласованного обратного преобразования; backup не заменяет сведения о совершённых после него эффектах. При неполных свидетельствах остаётся безопасная пауза.

## 10. Что требуется согласовать для начала реализации

Этот план предлагается утвердить как границу P0: 27 production-файлов, указанные тесты/fixtures, последовательность P0.1–P0.5 и критерии A01–A12. Дополнительно явно предлагаются три технических уточнения:
