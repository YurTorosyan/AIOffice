# Stage 4A — Lead Developer pilot

Only employee `lead` is connected. The other seven keep their IDs, roles and Skills and receive no real tasks. Mock remains the startup default. No dependency on a Codex SDK is added to the browser or npm dependencies.

## Run

Use Node 22.14+ (tested 24.18) and the reviewed **codex-cli 0.144.5**. The bridge fails closed for another CLI version until its protocol is reviewed. Sign in with `codex login` in your own terminal if needed; the office does not accept credentials.

```powershell
npm run build
npm run bridge
```

Open `http://127.0.0.1:8787`. Select **Codex pilot →**, **Подключить**, then **Задание на чтение**. Keep the terminal open. The bridge serves the production build and starts Codex only on Connect. After server-code changes, stop the bridge with Ctrl+C and restart it. For development run `npm run dev` in a second terminal; Vite proxies the same-origin `/api/codex` requests to port 8787.

The bridge attaches complete SHA-256-stamped snapshots of exactly 12 allowlisted project files (including the actual Lead TOML), canonicalized inside the repository and size-limited to 200 kB total. No path can be supplied by HTTP. This avoids shell/file tool execution when a nested Windows sandbox helper is unavailable. The agent is instructed to analyze only these snapshots and the three Skill inputs, use the plan tool if available, and never invoke shell/filesystem/network tools or request escalation. The fixed first task asks Lead to inspect project instructions and code, apply its three verified Skills, and return an ordered plan, evidence, acceptance checks, risks and Director decisions. It does not implement the plan or connect anyone else. Results are rendered as text, never HTML. **Остановить** requests interruption; only a terminal Codex event confirms that it stopped. **Отключить** closes the bridge-owned child process; an unconfirmed task becomes an error, never Completed. Browser reload returns to mock; it does not stop an active runtime. Reopen pilot controls to inspect/stop it. The real pilot stores its latest task/result and up to 200 event summaries in memory; restart clears them. Browser Activity shows the latest 80 summaries, 20 visible.

## Method and source verification

Official sources consulted: [App Server](https://learn.chatgpt.com/docs/app-server), [SDK](https://learn.chatgpt.com/docs/codex-sdk), [Developer commands](https://learn.chatgpt.com/docs/developer-commands), [Custom agents](https://learn.chatgpt.com/docs/agent-configuration/subagents), [Environment variables](https://learn.chatgpt.com/docs/config-file/environment-variables), [Configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference). App-server supports client integration with streamed events and approvals; SDK targets server-side automation. Stdio avoids exposing Codex's experimental WebSocket listener. The app-server itself remains experimental.

The installed CLI's `--version`, `--help`, `app-server --help`, `app-server generate-json-schema --help` and generated stable schemas were inspected. Generated schemas are research artifacts under ignored `work/codex-protocol`, not an invented HTTP API. Current online documentation has capabilities this installed version does not expose; the bridge uses only the reviewed subset below.

Local wire contract, generated by 0.144.5:

| Operation | Evidence/handling |
|---|---|
| `initialize`, then `initialized` | ClientRequest: ClientInfo name/version; JSONL stdio handshake |
| `account/read` | GetAccountParams `refreshToken: false`; expose boolean only, never account identity/tokens |
| `skills/list` | SkillsListParams cwds/forceReload; require enabled exact name AND canonical physical path |
| `thread/start` | ThreadStartParams cwd/developerInstructions/read-only/on-request/user/ephemeral; verify returned sandbox and approval policy |
| `turn/start` | TurnStartParams threadId/input, explicit skill inputs name/path, readOnly sandboxPolicy with networkAccess false |
| `turn/interrupt` | TurnInterruptParams threadId/turnId; wait for terminal turn event |
| `item/commandExecution/requestApproval`, `item/fileChange/requestApproval` | Response decision decline, only after Director presses Reject |
| `item/permissions/requestApproval` | Response permissions {} and scope turn, only after rejection |

Notifications consumed: `turn/started`, `turn/plan/updated`, `item/started`, `item/completed`, `item/agentMessage/delta`, `turn/completed`, `error`. Raw command output, reasoning deltas, raw stderr and account details are not relayed to the browser. Unexpected server requests are rejected with an unsupported-method response. No automatic grants, persistent allow rules or arbitrary user-input tool responses are implemented.

## Profile and Skills

`loadLead()` reads the existing `.codex/agents/lead-developer.toml`, validates its expected multiline-literal layout, hashes it and passes its actual developer instructions to the root thread. There is no stable named-root-agent selector in the inspected ThreadStartParams. This is **explicit profile loading by the bridge**, not a claim that app-server selected a named subagent automatically. No subagent is spawned, including for Technical Reviewer.

Before Connect and before task submission, physical installations are checked against the Stage 3B pinned receipts. Runtime discovery must report enabled Skills at those same canonical paths. The task explicitly sends three `skill` inputs: `planning-and-task-breakdown`, `context-engineering`, `code-review-and-quality`. A registry entry or discovery result alone does not prove the task applied a Skill: evidence from the actual real run is recorded separately in STAGE4A-REPORT.md.

## Boundaries

`server/rpc.mjs` manages the subprocess, JSONL framing, request correlation, timeouts, errors and shutdown. `server/pilot.mjs` owns the Lead lifecycle. `server/http.mjs` exposes only the fixed pilot actions. `RealCodexAdapter` projects normalized bridge snapshots into Agent/Task/Event state. React observes the shared adapter contract and never sends Codex protocol messages.

The bridge listens only on 127.0.0.1. Host/Origin checks, JSON size/content validation and a per-process CSRF nonce protect the browser endpoints. No CORS, generic RPC, shell, path, prompt, model or approval-grant endpoint exists. Static serving is confined to known build file types inside dist. Other local processes with the user's authority remain trusted; this is not a multiuser service or production authorization system.

Thread and turn enforce read-only sandbox and networkAccess false for model tools, with on-request approvals routed to the user. Permission escalation/writes cannot be approved in this pilot. Codex itself still needs network access to its model service and writes its own state outside the project. Read-only is not a per-project read allowlist: normal Codex read access and the user's existing Codex configuration still apply. The fixed developer instructions prohibit shell/filesystem/network tools, escalation, secrets, external paths, scripts and delegation; the UI must not be represented as a general-purpose hardened secret-isolation service. Do not point it at sensitive repositories without a separate policy review.

The bridge never reads credential files or exports environment variables/account data. Codex uses its own existing authentication. `AI_OFFICE_CODEX_BIN` may select a trusted executable from the launching terminal; it cannot be set over HTTP. On Windows the default is the official executable under LOCALAPPDATA/Programs/OpenAI/Codex/bin; `.cmd` wrappers are not run through a shell. If CODEX_HOME is absent, USERPROFILE/.codex is supplied privately to the child, fixing home detection without reading auth files. Do not copy auth files, change ACLs, disable sandboxing or start another user's daemon to work around permission failures.

Run the bridge in the signed-in user's ordinary terminal if an agent-launched process cannot open Codex's own state. A successful `codex login status` does not prove app-server can start or that a task can finish. CLI, bridge, authentication, discovery, thread start and completed turn are separate checks.

## Validation

`npm test`, `npm run validate:agents`, `npm run build`. Automated runtime tests use clearly labeled fixtures, including missing CLI/auth/discovery, transport framing, confirmations, policy rejection, final-result timing, interruption/disconnect and hostile HTTP requests. The original mock tests run without a Codex executable or running bridge. Real end-to-end evidence and browser results are recorded in STAGE4A-REPORT.md; fixture events are never proof of real integration.
