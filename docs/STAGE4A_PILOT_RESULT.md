## Предлагаемый упорядоченный план

### 1. Director gate и контракт следующего этапа

Зафиксировать отдельное решение Director о целях, разрешениях и порядке подключения.

Критерии приёмки:

- Определены read-only и write-возможности каждой роли.
- Решены режим последовательности, лимиты параллелизма и approval flow.
- Подтверждено, что mock остаётся доступным и стартовым.
- Установлено, меняется ли реальный workflow или сохраняется существующий mock-маршрут.

Зависимости: нет. Объём: S, документационное решение.

### 2. Общая runtime-модель нескольких сотрудников

Спроектировать конфигурацию сотрудника из `registry.json` и существующего TOML без выдуманного выбора профиля в API Codex. Отделить wire events от `OfficeState`.

Критерии приёмки:

- Только фиксированные семь employee IDs могут быть добавлены.
- Профиль и Skills загружаются по точному пути и только при `installed`.
- Для каждого turn существуют employee/task/thread correlation IDs.
- `waiting`, approval, interrupt, disconnect, failed и completed различаются явно.
- UI не содержит runtime-бизнес-правил.

Зависимость: задача 1. Объём: M.

### 3. Границы безопасности и жизненного цикла

До подключения новых ролей расширить allowlist и протокол моста, не создавая generic RPC, shell или prompt endpoint.

Критерии приёмки:

- Мост остаётся loopback-only.
- Credentials и env-значения не передаются браузеру.
- Нет автоматического повышения sandbox/approval.
- Disconnect и restart не превращаются в успешное завершение.
- Один сотрудник не может получить профиль или thread другого.

Зависимость: задача 2. Объём: M.  
Checkpoint: архитектурное и security-согласование Director до подключения первого сотрудника.

### 4. Подключение advisory-ролей по одной

Предлагаемый порядок: UI/UX Designer → SEO Specialist → Security Engineer. Начать с read-only анализа, поскольку эти роли могут выдавать артефакты без изменения рабочего дерева.

Для каждого сотрудника отдельная задача и отдельное решение запуска:

- загружается его TOML;
- разрешаются только Installed Skills;
- результат помечается реальным источником `codex`;
- кандидатные `ui-ux-pro-max`, `programmatic-seo`, `differential-review` не вызываются;
- роль не выходит за свою область.

Зависимость: задачи 2–3. Объём каждой: S–M.  
Checkpoint: тесты и ручная проверка после каждого сотрудника.

### 5. Подключение QA Engineer

Добавить проверяемый read-only QA-turn и только отдельно разрешённое browser/CUA-взаимодействие.

Критерии приёмки:

- QA сообщает фактические команды и результаты, не выдумывает прохождение тестов.
- `webapp-testing` не запускает непроверенные bundled scripts.
- Ошибка или недоступное окружение отображаются как ограничение, а не pass.

Зависимость: задача 4. Объём: M.

### 6. Подключение Frontend и Backend

Подключать только после отдельного решения Director о записи. Frontend ограничить существующим React/Vite-приложением; Backend — контрактами и данными в явно согласованном объёме.

Критерии приёмки:

- Запись ограничена задачей и рабочим каталогом.
- Frontend не меняет утверждённый pixel-art дизайн без решения Director.
- Backend не создаёт сервер, auth, cloud или платежи по умолчанию.
- Каждая мутация имеет diff, тесты, build и откатный путь.

Зависимость: задачи 3–5 плюс write-authorization. Объём: отдельные M-срезы.

### 7. Technical Reviewer — последним независимым gate

Reviewer получает завершённый diff read-only и не реализует исправления.

Критерии приёмки:

- Reviewer отделён от автора и Lead.
- Выводы содержат severity, доказательства и проверки по пяти осям.
- Lead может координировать исправления, но не заменяет verdict.
- Успех workflow невозможен без фактического review outcome.

Зависимость: задача 6. Объём: M.

### 8. Итоговый checkpoint

Проверить целостность registry/профилей, тесты, build, browser behavior, mock fallback и реальный end-to-end маршрут. После отчёта остановиться для решения Director; следующий этап автоматически не начинать.

## Checks

- PASS — соблюдён read-only режим; исходники не изменены.
- PASS — профиль Lead и три назначенных Skills применены.
- PASS — наблюдаемые факты отделены от предложений.
- PASS — самопроверка: план соответствует требованиям, сохраняет слои, не вводит generic endpoint/секреты, ограничивает параллелизм и разбит на проверяемые задачи.
- NOT RUN — `validate:agents`, тесты, build, browser check и git status: выполнение инструментов запрещено пилотом.
- NOT RUN — независимый Technical Reviewer verdict: изменений для review нет, Reviewer не подключён.

## Risks or open decisions

- Нужен выбор Director: все семь остаются read-only или Frontend/Backend получают ограниченную запись.
- Нужен утверждённый реальный workflow: существующий mock-маршрут не описывает участие всех специалистов.
- Параллельные turns могут конфликтовать за задачу и рабочее дерево; безопасный default — последовательное подключение.
- Candidate Skills нельзя использовать до полной проверки и установки.
- Точный перечень затрагиваемых runtime-файлов следует определить отдельным авторизованным чтением перед реализацией.
