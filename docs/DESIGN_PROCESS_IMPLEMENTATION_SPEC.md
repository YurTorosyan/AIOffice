# ТЗ: визуальные концепты и приёмка дизайна в AI Office

Дата: 23 ноября 2026. Статус: спецификация для согласования, не реализовано.

## 1. Цель и границы

Ввести обязательную проверяемую цепочку для новых задач с пользовательским интерфейсом:

Бриф → референсы → два визуальных концепта → решение Director → handoff →
пилот Frontend → проверка дизайнером → остальная реализация → функциональный QA →
визуальная проверка дизайнером → отдельная приёмка Director → итог Lead.

Два обязательных пользовательских решения:

1. **Concept approval**: утверждение одного конкретного концепта и версии до запуска UI-реализации Frontend.
2. **Visual acceptance**: приёмка конкретной реализованной версии после просмотра фактических экранов.

PASS функционального QA, Security, Reviewer или самого дизайнера не заменяет ни одно решение Director.
Утверждение концепта не разрешает применение файлов, запуск тестов, новые инструменты или публикацию.

Сохранить офис, персонажей, анимации, ровно восемь работников, их ID и роли, Skills,
Real/Mock, проектную изоляцию, checkpoints и существующий broker применения файлов.
Director остаётся владельцем, а не девятым работником.

**Готовый ARMGARAGE не мигрировать и не открывать заново.** Его workflow
`cf87600a-5cfd-46b3-8bb1-fe506684b2f9` остаётся COMPLETED; файлы
`C:\Projects\ArmGarage`, результаты, approvals и история сохраняются.
Coffee House не затрагивать. Реализацию и проверки вести на отдельном синтетическом проекте.
Редизайн существующего сайта в будущем оформляется отдельным workflow с явным решением владельца.

## 2. Что меняется относительно текущего приложения

Сейчас `design` соответствует работнику `design` и Skill `frontend-design`;
результат спецификации — текстовый JSON/handoff. Согласования `apply_changes` и
`run_tests` предназначены для эффектов broker, а не для оценки внешнего вида.
Нативные сотрудники работают read-only по переданным снимкам и не имеют произвольного shell/network.

Следовательно, недостаточно добавить текст в prompt дизайнера. Нужны:

- отдельные модели дизайн-пакета, визуальных артефактов и пользовательских решений;
- создание и просмотр реальных макетов, а не ссылки на несуществующие изображения;
- проверка согласования в scheduler и перед запуском исполнителя;
- отдельная визуальная проверка фактической реализации;
- хранение версий, доказательств и решений после перезапуска;
- явный критерий COMPLETED, включающий визуальную приёмку.

## 3. Применимость и ответственность

При создании **нового** workflow сохранять `designProcessVersion: 1` и режим
`required` для сайтов, лендингов и других задач с созданием/редизайном UI.
В карточке новой задачи Director видит включённый режим до старта.
Lead не может снять этот режим своим JSON. Для задачи без UI допустим `not_applicable`
с сохранённой причиной; спорная классификация требует решения Director.

Режим не включается ретроспективно для существующих workflows без поля версии.
Явное изменение режима записывается как решение Director; обычная кнопка
«Продолжить» или общее разрешение технических действий не отключает визуальные этапы.

| Участник | Ответственность |
| --- | --- |
| Lead | Бриф, граф зависимостей, проверка полноты handoff, итог по всем обязательным этапам |
| UI/UX Designer (`design`) | Референсы, концепты, визуальная система, комплект материалов, сравнение реализации с концептом |
| Frontend (`frontend`) | Реализация только утверждённой версии, сначала пилот, затем оставшаяся страница |
| QA (`qa`) | Функциональность, адаптивность, доступность и фактические browser receipts |
| Reviewer (`review`) | Независимое техническое ревью; его APPROVED не означает одобрение дизайна владельцем |
| Director | Выбор версии концепта, существенные изменения направления, окончательная визуальная приёмка |

Backend и другие независимые задачи могут идти параллельно, если не реализуют заблокированный UI.
Зависимости выводятся из утверждённого плана и назначения файлов, а не только из названия роли:
перенос UI-задачи к Backend не должен обходить согласование концепта.

## 4. Обязательные результаты этапов

### 4.1. Бриф

Один версионируемый документ: цель, аудитория, основное действие пользователя,
характер бренда, структура страницы, обязательные сценарии, язык, устройства,
предпочтения и запреты, доступные изображения/логотип/шрифты.
Неуказанные сведения отмечать как предположения или вопросы, не выдумывать факты компании.

### 4.2. Референсы

3–5 конкретных примеров. Для каждого: URL/локальный источник, название,
какая страница реально просмотрена, дата просмотра и происхождение снимка,
пояснение по композиции, типографике, изображениям и взаимодействиям,
а также что не следует переносить.

Статусы источника: `verified`, `unverified`, `unavailable`.
Непроверенные источники можно показать как кандидаты, но не считать изученными.
Референс не означает лицензию на копирование его фотографий, шрифтов или кода.
Для материалов, передаваемых в реализацию, обязательны источник и условия использования.

На MVP отдельное обязательное согласование референсов не добавлять: Director может
исправить направление до концептов. Обязательное решение — по визуальному пакету ниже.

### 4.3. Два визуальных концепта

Два существенно разных направления на одном брифе и сопоставимом содержании.
Для каждого обязательны:

- главный экран и не менее двух характерных следующих секций;
- desktop 1440 px и mobile 390 px;
- карточка, CTA, форма или диалог и примеры focus/error/busy/selected;
- типографика, цвет, сетка, плотность, графика и её происхождение;
- реальные изображения либо явно подписанные материалы, которые ещё нужно заменить.

Для короткого интерфейса вместо трёх секций показывать полный экран и его ключевые состояния;
это исключение фиксируется в брифе. Макет должен позволять оценить композицию страницы,
а не только логотип, персонажа или изолированную карточку.

Не принимать как визуальный концепт: текстовое описание, moodboard без экрана,
блок-схему, wireframe, пустую ссылку, отсутствующий файл либо изображение с обещанием «доделаем позже».
Изменение только акцентного цвета не образует второе направление.

При отсутствии необходимых графических материалов — `waiting_assets`, с точным списком
недостающего. CSS может задавать композицию и состояния, но не подменяет требуемую
фотографию/иллюстрацию набором примитивных фигур. Проверка наличия файлов не доказывает
художественное качество: конечное решение остаётся за Director.

### 4.4. Handoff утверждённого концепта

Выбранный concept ID/version и хеши изображений; бриф; design tokens;
шрифты и источники; размеры, spacing, сетка и адаптивные правила для 390/768/1440;
компоненты и состояния; реестр готовых/недостающих assets; критерии визуальной приёмки;
область пилота; ограничения концепта.

Для визуально важных частей запретить неявные решения Frontend «по своему вкусу».
Пробелы в handoff возвращать дизайнеру как конкретные вопросы, не перезапуская выполненные задачи.
Frontend получает не только JSON, но и доступные ему утверждённые изображения.
Если установленный runtime не может принять изображения через проверенный контракт,
фиксировать ограничение до старта: текстовый пересказ нельзя выдавать за просмотр макета.
Способ передачи изображений сверять с локальным протоколом установленного Codex;
новый внешний API не придумывать.

### 4.5. Пилот и визуальная приёмка

Пилот: главный экран + одна характерная секция/ключевое состояние, desktop/mobile.
Дизайнер сравнивает фактический рендер с утверждённым концептом; остальная UI-реализация
ожидает результат `matches_concept` или список конкретных исправлений.
Отдельного третьего обязательного решения Director по пилоту нет; карточка доступна ему,
а существенное изменение направления возвращает процесс к concept approval.

После реализации нужны фактические screenshots из текущей production-сборки
на 390/768/1440, проверенные состояния элементов и отчёт дизайнера по отличиям.
Screenshot должен храниться как изображение, доступное в карточке: один SHA-256 в логе
не является просматриваемым доказательством внешнего вида. Нельзя подменять рендер
реализации изображением концепта или принимать изображение без привязки к сборке.
Сравнивать: композицию и иерархию, типографику, изображения, отступы/плотность,
цвета/контраст, адаптацию, состояния и соответствие характеру бренда.
Замечание содержит экран, viewport, элемент, ожидаемый вид, фактическое отличие,
серьёзность и исходные artifact IDs. Числовой «рейтинг красоты» не является разрешением.

Director получает сравнение концепт/реализация и решения:
«Принять внешний вид» / «Вернуть на доработку».
Значимое несоответствие нельзя автоматически принять из-за PASS тестов.

## 5. Данные и неизменяемые решения

Отдельный доменный модуль `src/design/`; React не определяет допустимость переходов.
Не раздувать общие статусы Agent State. Дизайнер при ожидании решения имеет
обычный `waiting`, а подробный этап хранится в Design Process.

| Сущность | Обязательные поля |
| --- | --- |
| DesignProcess | version, id, projectId, workflowId, mode, briefVersion, phase, activeRevisionId, selectedConceptRef, acceptedVisualRef, createdAt, updatedAt |
| DesignRevision | id, processId, revision, briefRef, referenceRefs, concepts, handoffRef, previousRevisionId, completeness, createdBy, createdAt |
| Concept | id, title, direction, desktopArtifactIds, mobileArtifactIds, stateArtifactIds, assetManifestRef, limitations |
| DesignArtifact | id, projectId, workflowId, taskId, kind, MIME, bytes, width, height, sha256, provenance, sourceLicense, completeness, createdAt |
| DesignDecision | id, requestId, projectId, workflowId, kind, revisionId, conceptId, artifactHashes, decision, feedback, actor=director, createdAt |
| VisualEvidence | id, conceptDecisionId, implementationRevision, buildManifestSha256, renderOperationId, viewportArtifacts, designerReviewRef, completeness |

Виды артефактов: `reference`, `concept`, `handoff`, `asset`, `implementation_screenshot`, `visual_review`.
Двоичные файлы и полный отчёт не помещать в workflow JSON/base64 или prompt:
хранить ссылки и хеши; при запуске передавать только относящиеся к задаче материалы.

Решение концепта связывается с конкретным брифом, пакетом, concept ID, версиями и хешами.
Оно не становится «одобрением всех последующих вариантов».
Visual acceptance дополнительно связывается с implementation revision, точной сборкой,
фактическими screenshots и соответствующим утверждённым концептом.
Отсутствующие, подменённые или неполные артефакты не позволяют принять решение.

Успешное решение записывается атомарно и идемпотентно по requestId.
Повтор запроса с тем же содержимым возвращает прежний результат;
с тем же requestId и другим содержимым отклоняется как конфликт.
Model output не может содержать действующее решение Director.

## 6. Переходы и блокировки

Основные фазы: `brief`, `references`, `concepts`, `waiting_assets`,
`awaiting_concept_approval`, `handoff`, `frontend_pilot`, `pilot_review`,
`frontend_implementation`, `visual_review`, `awaiting_visual_acceptance`, `accepted`.
Остановка workflow — существующий pause/checkpoint, а не потеря текущей фазы.

| Действие | Предусловие и результат |
| --- | --- |
| Отправить концепты на согласование | Два полных сравнимых концепта, проверяемые файлы; иначе понятный список недостающего |
| Утвердить концепт | Явное решение Director на текущую версию; снимает только дизайн-блокировку UI-задач |
| Вернуть концепт | Комментарий обязателен; сохраняет прежний пакет, создаёт новую ревизию; Frontend не запускается |
| Начать UI-пилот | Утверждённый концепт + полный handoff + обычные права/зависимости существующего scheduler |
| Начать оставшуюся UI-реализацию | Пилот соответствует концепту; смена направления требует нового решения Director |
| Отправить реализацию на визуальную приёмку | Полные screenshots текущей сборки и отчёт дизайнера, без блокирующих визуальных замечаний |
| Принять внешний вид | Director принимает текущую VisualEvidence; решение не заменяет QA/Security/Reviewer |
| Вернуть реализацию | Замечания относятся к конкретной версии; создаются только нужные scoped исправления |
| Завершить workflow | Все технические этапы пройдены и действующая visual acceptance относится к текущей реализации |

Проверять concept approval при расчёте ready-задач, при preflight исполнителя,
при выдаче handoff и перед применением UI-proposal. Одного disabled в React недостаточно.
«Продолжить», прямой start, retry, смена task ID, восстановление checkpoint и
переименование типа задачи не обходят серверную проверку.

Утверждение концепта допускает запуск задачи в уже работающем workflow только по обычным
правилам scheduler. Если workflow глобально на паузе, решение его не возобновляет.
Ожидание решения по дизайну не останавливает независимые разрешённые задачи автоматически.

Новая редакция утверждённого пакета не перезаписывает старую. При смене активного концепта
выполнение зависимого UI сначала доводится до подтверждённой паузы; готовые файлы сохраняются.
Дальнейшая работа оформляется как ограниченный diff, не полная перезапись сайта.
До совпадения новой версии handoff и согласования старые UI-proposals неприменимы.

Изменение кода, CSS или assets, влияющих на принятый внешний вид, делает прежнюю
visual acceptance исторической: нужны свежий рендер и новая приёмка. Утверждённый концепт
при этом не отменяется автоматически, если направление не менялось.
При несовпадении revision без надёжного доказательства отсутствия визуального влияния
использовать консервативное правило: запрашивать новые screenshots, не подменять старые.

Лимиты: не более двух автоматических доработок концепта и двух пилотных доработок;
счётчик общий для lineage, новые IDs не обнуляют его. Дальше — сохранение и решение Director.
Это отдельные счётчики дизайна; существующий лимит 0–3 циклов исправления реализации не повышать.

Сохранить существующий TaskType `design` и восемь работников. Для новых узлов использовать
отдельные `TeamSpec.kind`: `design_concept`, `design_handoff`, `visual_review`,
все назначаются работнику `design`; пилот и остальная реализация остаются `frontend`.
Новые проверки дизайна добавляет и валидирует оркестратор. Модель Lead не может
переназначить владельца решения Director или представить обязательный этап как необязательный.
Не начатая UI-задача остаётся `pending` с отдельной причиной ожидания дизайна,
а не фиктивной ошибкой сотрудника.

## 7. Создание макетов и работа с графикой

В текущем bridge нет подтверждённого image-generation API. Не добавлять фиктивный вызов
Codex «нарисовать» и не объявлять изображение созданным из-за строки с его именем.

Обязательный базовый механизм внедрения:

1. Дизайнер read-only предлагает отдельный **design draft**, не патч проекта:
   полный статический HTML/CSS макет с локальными ссылками на зарегистрированные assets.
2. Broker принимает ограниченный draft в собственное хранилище артефактов после
   проверки схемы; исходники пользовательского проекта не меняются.
3. Новый фиксированный профиль `design_render` рендерит draft в одноразовом
   изолированном Chromium на 1440/390 и выдаёт реальные PNG/WebP + manifest.
4. В draft запрещены JS, event handlers, формы отправки, iframes, внешние URL ресурсов,
   произвольные команды и чтение хоста. Разрешены только переданные HTML/CSS и
   whitelist raster assets. Рендерер не делает установку зависимостей.
5. Подготовленные вне приложения качественные макеты можно импортировать как PNG/JPEG/WebP
   через тот же artifact broker: это поддерживаемый способ, а не автоматическое доказательство качества.

Первичные графические assets берутся из материалов владельца, явно разрешённых источников
либо отдельно подключённого проверенного генератора. Если их нет и без них концепт
не соответствует брифу, этап остаётся `waiting_assets`. Наличие статического рендерера
не разрешает заменять фотографии и сложную графику простыми CSS-заглушками.

Автоматический веб-поиск референсов и генератор изображений оформляются как отдельные
host-side providers с явными доступностью, происхождением и согласованными полномочиями.
Сотрудникам не выдавать общий network/shell. На базовом пути допускаются ссылки и снимки
владельца; нельзя считать страницу изученной, если доступ к ней фактически не получен.
Интеграцию конкретного внешнего provider выполнять только по проверенной документации;
его отсутствие показывать прямо, без имитации результата.

Для рендера реализованного сайта нужен отдельный профиль `implementation_capture`:
он принимает только проверенный архив production assets с известными build receipt,
source revision и manifest hash. В отличие от статического concept draft, React/JS
здесь выполняется внутри изолированного браузера, как в существующем QA, без внешней
сети и host tools. Нельзя открывать произвольный пользовательский URL вместо сборки.

Production assets сохраняются при успешной сборке в отдельном project-bound архиве.
Если точная сборка уже есть, визуальный capture использует её без повторных Vitest/build;
если архива нет или hashes изменились, показывает необходимость отдельной новой сборки.
Screenshots передаются из одноразового контейнера по фиксированному ограниченному
каналу экспорта артефактов, с проверкой MIME/размера/хеша и receipt операции.
Не переносить PNG как неограниченную строку в console output и не открывать общий host mount.
Внедрение архива не переписывает старые build receipts и не выдаёт существующий только
хеш за восстановленные bytes. Автоматическое удаление renderer-контейнера допустимо
только после подтверждённой архивации результата или сохранения явного состояния сбоя.

Draft и bitmap-артефакты не расходуют восемь source/test путей implementation plan.
Это отдельное хранилище с отдельными строгими лимитами, а не обход projectPath.
Перенос готового изображения в сайт требует отдельного проверенного asset-import действия
broker: точные bytes/hash и namespace `public/design-assets/<sha256>.<ext>`.
Не расширять общий текстовый `apply_changes` до произвольной бинарной записи.
Если UI-задача требует новый публичный asset, Lead включает его отдельный утверждаемый
импорт в план; без готового импортированного файла задача сообщает блокер.

## 8. Хранение, безопасность и восстановление

Метаданные процесса: центральное проектное состояние рядом с workflow/checkpoints;
payload артефактов: проектное `.ai-office/design-artifacts/` через WorkspaceBoundary.
Хранить manifest с project/workflow/task ID, MIME, размером и хешем; ответы модели —
в прежнем ResultArchive. Версии неизменяемые, журнал решений append-only.

Предлагаемые пределы MVP: один raster ≤10 MiB, ≤16 млн пикселей и ≤16384 px на сторону;
дизайн-пакет ≤64 MiB и ≤12 raster-файлов; draft ≤6 HTML/CSS файлов, ≤200000 UTF-8 bytes.
Неполный импорт и превышение лимита дают видимый блокер; не обрезать файл и не объявлять его готовым.
Полные изображения допускается хранить отдельно от workflow и передавать модели
с проверенной адаптацией размера, не выдавая уменьшенную копию за оригинал.

Проверять сигнатуру файла и декодирование, а не только расширение. Исходные SVG,
HTML и архивы не принимать как безопасные пользовательские изображения.
Draft HTML/CSS — только вход изолированного рендерера, не inline-HTML в панели управления.
Превью в AI Office — проверенный raster, без скриптов и внешних запросов.
Файлы, URL и тексты референсов считать недоверенными данными, не инструкциями агенту.

Использовать существующую аутентификацию localhost bridge, project binding, CAS,
идемпотентность и журналирование. Не создавать endpoint произвольного чтения пути/URL,
shell или обхода approval. `design_render` — отдельное разрешаемое действие,
не неявный подвид `run_tests`. Изоляция обязательна: fixed image, network none,
read-only root, non-root, seccomp/no-new-privileges, bounded memory/pids/output/time.
Учитывать уже выявленный screenshot file-limit: достаточный ограниченный буфер,
никакого отключения sandbox ради скриншота.

Сбой после решения Director, повторный HTTP-запрос и рестарт должны восстанавливать
одно решение и один hash-bound набор материалов. При неизвестном исходе не запускать
повтор рендера/применения автоматически. Потеря файла не создаёт новую версию согласия.
Межпроектная ссылка, stale hash или испорченный журнал блокируют действие с сохранением оригинала.

## 9. UI без переделки офиса

В существующих карточках управления добавить карточку «Дизайн проекта»:
фаза, ответственное лицо, версия, выбранное направление, ожидаемое действие и причина блокировки.
Не превращать экран в новую административную панель.

- Концепты: две карточки с большими desktop/mobile превью, полноэкранным просмотром,
  описанием отличий, референсами и готовностью assets. Кнопки
  «Утвердить этот концепт» / «Вернуть с замечаниями».
- У кнопки явно указаны concept ID и версия. Один вариант не выбран заранее.
  Вернуть без комментария нельзя; история решений доступна ниже.
- Frontend: «Ожидает утверждения концепта vN» вместо неясного pending;
  после согласования — ссылка на выбранный пакет.
- Приёмка: рядом концепт и фактический рендер, переключатель 390/768/1440,
  список отличий и кнопки «Принять внешний вид» / «Вернуть на доработку».
- Функциональный QA и визуальная приёмка показываются отдельными статусами.
  «69 тестов PASS» не окрашивает визуальную карточку в «Принято».
- При потере соединения — известный результат и состояние сверки; не показывать
  ложное успешное решение. Управление доступно с клавиатуры, подписи и focus видимы.

## 10. Команды и события

Предлагаемый отдельный ограниченный API `design` поверх существующей сессии bridge:
snapshot, импорт артефакта, submit_revision, approve_concept, request_concept_changes,
submit_visual_evidence, accept_visual, request_visual_changes.
Это проектируемый контракт AI Office, не API Codex.

Решения принимают projectId, workflowId, processId, revision/evidence ID,
expected manifest hash, requestId и комментарий; содержимое решения не берётся из model output.
Запуск рендера идёт через отдельный exact approval broker, не через произвольный командный endpoint.

Все события — в Activity Log: brief_saved, references_prepared, concepts_rendered,
concept_submitted, concept_approved, concept_changes_requested, handoff_ready,
frontend_blocked_by_design, pilot_reviewed, visual_evidence_submitted,
visual_accepted, visual_changes_requested, visual_acceptance_stale,
design_artifact_failed, design_recovery_required. У каждого есть владелец проекта,
workflow, task/revision, timestamp и связанные decision/artifact IDs.
Повтор доставки не дублирует решения и задачи.

## 13. Порядок внедрения и приёмки

1. **Контракт и сохранность:** models/policy, архив артефактов и решений,
   backward compatibility, schema и migration tests. Никаких реальных задач.
2. **Визуальный пакет:** безопасный импорт, design draft renderer и две реальные
   версии концепта на синтетическом проекте; карточки и решения Director.
3. **Пилот Frontend:** серверная блокировка до approval, полная передача утверждённых
   материалов, визуальная проверка пилота и ограниченные исправления.
4. **Финальная приёмка:** screenshots текущей сборки, сравнение и отдельное решение
   Director; привязка к финальному COMPLETED; восстановление после рестарта.
5. **Общий приёмочный прогон:** D01–D22, существующие тесты/build/browser,
   подтверждение неизменности ARMGARAGE, отчёт о реально доступных providers.

Система считается внедрённой только после сквозного доказательства:
до выбора концепта UI-задача не стартует; после выбора реализует выбранную версию;
после PASS тестов без visual acceptance завершение невозможно;
после явной приёмки конкретной реализации workflow корректно завершается.
Наличие новых полей, красивых карточек или подключённого Skill без этих переходов
не считается выполнением ТЗ.
